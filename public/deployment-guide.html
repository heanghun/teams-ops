TEAMS Operations - Production deployment handoff

Prepared from the current V1 source. This is a deployment plan, not confirmation that production is configured.

Current delivery

- The existing public demo remains at https://operations.teams.com.kh/ with its existing data bindings. It must remain isolated from real records.

- English and Khmer interface switching is saved per browser. Official names, job titles, record codes, leading-zero IDs, typed content and approved exports retain their source spelling and language.

- Phone/tablet navigation, role-aware field shortcuts, card layouts, large controls, full-screen forms and safe-area spacing are implemented.

- A manifest, TEAMS launcher icons, Apple touch icon, versioned service worker, installation help and offline page are implemented. Installation depends on the browser/device; it is not an App Store release.

- The service worker caches an explicit list of public static assets only. It does not cache authenticated responses, employee data, messages, project records, uploads or API calls. It does not queue or replay writes.

- A cold offline launch shows bilingual reconnection guidance. Live work, approvals, stock movements and email require connectivity. The browser-local public demo is not a shared database or a sync engine.

- `/api/health` is a no-store liveness endpoint. It does not assert database, storage or mail-provider readiness.

Ordered deployment sequence

1. Confirm the Cloudflare Access application and operational owners for ops.teams.com.kh.

2. Create separate staging and production D1/R2 resources. Use host-provided bindings. Apply `drizzle/0000_operations.sql` and its journal through the deployment migration path once. Do not modify an already-applied migration or copy fictional records into the live database.

3. Verify that Cloudflare Access supplies identity and the correct audience. Disable alternate Worker URLs.

4. Create a protected staging deployment in `team` mode. Seed only real empty-system settings. The code rejects an initialized fictional database in team mode.

5. Complete production personnel migration/admin directory visibility and bind verified sign-in accounts separately. Reconcile the 69 source records, leading-zero IDs and unresolved organizational information. Supply approval grants from a documented TEAMS decision, independently of job title.

6. Import reviewed operational masters and reconciled opening balances into staging. Log source files, cutoff dates and control totals. Have the corresponding TEAMS function validate each master and balance.

7. Configure sender domain, SPF/DKIM/DMARC as supplied by the provider, receiving MX, `TEAMS_EMAIL_ROUTING` and the signed webhook. Ensure `/api/mail/webhook` can receive signed provider POSTs without exposing other authenticated API routes. Configure provider events and test external delivery/receiving/bounces with approved test addresses.

8. Configure backups, private object retention, malware handling, limits and monitoring. Restore a matching D1/R2 recovery point into a separate environment and record reconciled results.

9. Run the acceptance matrix below with distinct real test accounts and two devices. Review performance at expected data volume. Obtain TEAMS acceptance of English/Khmer copy and final documents.

10. Freeze legacy entry for the agreed cutover window, take a final verified backup/export, import the delta, reconcile and authorize the cutover. Do not erase legacy records. Retain a rollback point and known source/deployment version.

11. Publish the approved production version to the protected hostname. Monitor logins, writes, files, balances and email during the controlled pilot before wider activation.

Finance access and invoicing

Only authenticated director (Managing Director) and finance (Accounting & Finance Manager) profiles may read company receivables, overdue collections, claims, payments, cash forecasts and project financial positions. Platform administrators and auditors have no automatic financial override. Existing operational quotation and procurement pricing stays available to its authorized teams. In production, protect initial MD membership through an operator-reviewed bootstrap. Only the MD can grant, remove or modify protected director/finance account access; existing accounts are not automatically activated by this release.

The public demo deliberately permits switching into these profiles using fictional financial records. It is not an authentication boundary. Keep real financial and HR data out of this public demo. Production uses the authenticated team environment and ignores browser-supplied demo role headers.

Native commercial and tax invoices use T E A M S Co., Ltd. The address on teams.com.kh is a public contact address, not verified tax registration evidence. Finance must enter and verify the registered Khmer name, registered English/Khmer addresses, taxpayer category, VAT TIN, authorized signatory and supporting verification reference. Complete bilingual buyer and item descriptions, customer TIN for tax invoices, and an applicable daily KHR conversion with its date/source before real issuance. This workflow supports VAT on domestic USD/KHR services and materials; other tax types, credit notes, foreign-currency accounting and GDT filing require an accounting implementation and Finance review.

Drafts do not increase receivables. Issuance allocates a separate annual CI/TI number, freezes a company/customer/items/tax snapshot and records the event. Issued amounts cannot be edited. Unpaid native invoices can be voided with a reason while retaining their number; invoices with any payment history require an accounting credit-note process. Legacy invoice references and their existing payments remain available.

Invoice PDFs use embedded Noto Khmer/Latin fonts and fontkit shaping. Retain the bundled font and software licenses. Store final documents and audit history under the approved retention policy and verify actual target-device printing. Finance correspondence must use the restricted finance mailbox. Add a dedicated verified finance address in TEAMS_EMAIL_ROUTING, avoid routing it to general/installation/maintenance mailboxes, and review imported historical documents and mail classification before production.

The protected accounting export uses schema teams.invoice-export.v1 and stable invoice/payment IDs, line items, VAT, currency, issued snapshots, void status and payment reversals. It does not post a journal, file a tax return or synchronize a ledger. Before connecting an accounting product, implement provider authentication, account/tax/customer mappings, idempotent outbox processing, reconciliation, retries, credit notes and a controlled migration cutoff. Prevent double entry while legacy accounting remains authoritative.

Reference documents: GDT Notification implementing invoice Prakas 723, GDT commercial invoice instruction, TEAMS contact details. Validate current requirements and TEAMS registration evidence with Finance before live issuance.

Release commands and artifacts

- Runtime: Node.js 24+ for local checks and build. The production bundle runs as a Worker, not the Node development server.

- Checks: `npm test`, `npm run build`, `node --check dist/server/index.js`, `git diff --check`.

- Hosting artifact: `dist/server/index.js` with the generated Wrangler production configuration.

- Migration source: `drizzle/0000_operations.sql`, `drizzle/meta/_journal.json`.

- Liveness monitor: `GET /api/health`, expected 200 JSON `status: ok`. Test authenticated state, file storage and provider configuration separately.

- Rollback: redeploy the prior known source version only after checking data compatibility. Code rollback alone does not reverse operational records or provider sends.

Explicit launch blockers

A separate production environment, trusted identity and memberships, production personnel migration, real source-data reconciliation, provider configuration/delivery UAT, security/backup/restore checks and TEAMS departmental acceptance remain incomplete. Native invoices now embed Khmer and Latin fonts. Validate the invoice template and Khmer terminology with Finance before launch; the older quotation/agreement PDF engine still needs Khmer support for Khmer client documents. Automatic recurrence and general AI tender extraction remain separate implementation decisions. Do not represent this public demo as production-ready merely because it is installable.
